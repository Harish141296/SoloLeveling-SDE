Senior

A framework for ML system design

Senior engineers are paid to design whole systems under real constraints, not to know one more algorithm. The same applies in interviews. Use a consistent structure so you never freeze in front of a blank whiteboard.

  • 1. Clarify — turn the vague ask into concrete requirements and scale numbers.
  • 2. Frame as ML — what's predicted, what's the label, what's the metric, what's the baseline?
  • 3. Data — sources, labels, features, freshness, volume.
  • 4. Architecture — the components and how data flows through them.
  • 5. Scale & serve — online vs batch, latency, throughput, caching.
  • 6. Reliability, monitoring, cost — how it stays up, healthy, and affordable.
  • 7. Trade-offs — name what you'd do differently with more time/budget/data.
Key idea
Interviewers (and real stakeholders) care more about how you reason through trade-offs than about the 'right' answer. Think out loud; state assumptions explicitly.
Senior

Requirements & framing

Most weak designs fail here: jumping to a model before pinning down what success means. Separate functional from non-functional requirements and put numbers on everything.

  • Functional — what must it do? (e.g. 'recommend 10 items', 'answer from our docs with citations').
  • Non-functional — latency target (p99), throughput (QPS), availability, freshness, budget.
  • Scale math — users × requests × size = QPS and storage. Do the arithmetic out loud.
  • The metric — the offline metric you optimize and the online/business metric that actually matters.
Note
Always ask for numbers: 'How many users? What p99 latency is acceptable? How fresh must predictions be?' The architecture changes completely at 100 vs 100M users.

The anatomy of an ML system

Most production ML systems share the same skeleton. Learn it once and adapt it to any problem.

 data ->| ingestion |----->| feature     |----->| training     |
        | pipeline  |      | store       |      | pipeline     |
        +-----------+      +------+------+      +------+-------+
                                  |                    |
                                  v                    v
                           +------+------+      +------+-------+
            request -----> | inference   |<-----| model       |
                           | service     |      | registry    |
            response <-----+------+------+      +-------------+
                                  |
                                  v
                           +------+------+
                           | monitoring  | -> drift / quality alerts
                           +-------------+
  • Offline path — ingest → features → train → evaluate → register.
  • Online path — request → fetch features → model → post-process → response.
  • Shared — the feature store and registry connect both, preventing training/serving skew.
Advanced

Online vs batch & latency budgets

The first big fork: must predictions be computed per request, or can they be precomputed? This single choice reshapes the whole design.

  • Batch — precompute predictions on a schedule, store them, serve via lookup. Cheap, simple, but stale. Good for daily recommendations, risk scores.
  • Online — compute per request. Fresh, but you own latency and scaling. Required for search, fraud, chat.
  • Hybrid — precompute candidates in batch, rank online. The standard for large recommender/search systems.
Key idea
Budget your latency: if p99 must be 200ms and the model takes 80ms, you have 120ms left for feature lookup, network, and post-processing. Design within the budget from the start.
Advanced

Scaling & performance

Once one instance works, the question is how to handle 1000× the load without 1000× the cost or latency.

  • Horizontal scaling — many stateless inference replicas behind a load balancer; autoscale on traffic.
  • Caching — cache predictions/embeddings for repeated inputs; often the biggest single win.
  • Async & queues — decouple slow work; absorb spikes with a queue instead of dropping requests.
  • Model optimization — quantization, distillation, batching, GPU sharing to cut per-request cost.
  • Approximate methods — ANN indexes (FAISS, HNSW) for vector search at scale instead of exact kNN.
Senior

Reliability & graceful degradation

At scale, failures are constant, not exceptional. A senior design assumes components will fail and stays useful anyway.

  • Redundancy — no single point of failure; multi-AZ, replicas.
  • Graceful degradation — if the model times out, fall back to a simpler model, a cached result, or a sensible default. Never hard-fail the user.
  • Circuit breakers & timeouts — stop hammering a failing dependency; fail fast.
  • Idempotency & retries — safe to retry without double-processing.
Key idea
'What happens when the model service is down?' is a senior-defining question. The answer should never be 'the product breaks' — it should be a defined fallback.
Senior

Cost engineering

At scale, cost is a first-class design constraint — especially with LLMs, where a careless design can be 100× more expensive than a careful one for the same quality.

  • Right-size the model — use the smallest model that meets the quality bar; route easy cases to cheaper models.
  • Cache aggressively — repeated queries shouldn't pay twice.
  • Trim compute — shorter prompts/contexts, batching, quantization, spot instances for training.
  • Measure cost per request — make it a tracked metric, like latency.
Note
Frame trade-offs as a triangle: quality vs latency vs cost. You usually optimize two and accept the third. Say which, and why, for the given product.
Project

Design: a RAG knowledge assistant

'Build a chatbot over our company's 100k documents.' Walk the framework:

  • Requirements — grounded answers with citations, p99 < 3s, ~50 QPS, docs update daily.
  • Offline — ingest docs → chunk → embed → vector DB; re-index on change. Version the index.
  • Online — embed query → hybrid retrieve top-20 → rerank to top-4 → LLM with context → validate citations.
  • Scale/cost — cache embeddings and frequent answers; route to a smaller model when confidence is high.
  • Reliability — if retrieval fails, say 'I couldn't find that' rather than hallucinate; timeout + fallback model.
  • Eval/monitor — golden set for retrieval recall and answer faithfulness; track groundedness in production.
Note
Implementation details for this are in the LLM Engineering guide; serving in FastAPI; monitoring in MLOps.
Project

Design: a recommendation feed

'Recommend content for a 10M-user feed.' The classic two-stage pattern:

  • Candidate generation — cheaply narrow millions of items to ~hundreds (ANN over embeddings, co-occurrence). Often precomputed/batch.
  • Ranking — a heavier model scores those candidates per user, online, with fresh features.
  • Re-ranking — apply business rules: diversity, freshness, dedup, policy filters.
  • Features — from a feature store for train/serve consistency; cold-start handling for new users/items.
  • Metrics — offline (NDCG) gates deploys; online (engagement) via A/B tests is the real judge.
Key idea
The two-stage 'retrieve then rank' shape recurs everywhere — search, recommendations, and RAG are the same skeleton. Recognizing that pattern is senior-level fluency.
Senior

What separates a senior answer

Given the same prompt, the senior answer differs in posture, not vocabulary:

  • Starts with questions and assumptions, not a solution.
  • Proposes the simplest design first, then scales it as constraints demand.
  • Names failure modes and the fallback for each, unprompted.
  • Quantifies — latency budgets, QPS, cost per request.
  • States trade-offs explicitly and defends the choice for this context.
  • Knows when not to use ML, or not to use the biggest model.
Try it
Take any product you use daily and design its ML system end to end on paper using the framework. Do this weekly — it's the single best preparation for senior interviews and real architecture work.
