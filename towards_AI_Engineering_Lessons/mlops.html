Core

The production gap

A model in a notebook has zero value. MLOps is the engineering discipline of getting models into production reliably and keeping them healthy over time. It's the skill that most separates senior engineers from talented experimenters.

  • Reproducibility — anyone can recreate any result from code + data + config.
  • Automation — training, testing, and deployment run without manual heroics.
  • Observability — you know how the live model behaves and get alerted when it drifts.
  • Governance — every model is versioned, traceable, and rollback-able.
Key idea
ML systems rot in ways normal software doesn't: the code is fine but the world changes, the data drifts, and accuracy quietly decays. MLOps is how you catch and fix that.
Core

Reproducibility & experiment tracking

Hundreds of experiments with slightly different configs are impossible to manage from memory. A tracker logs params, metrics, and artifacts for every run so you can compare and reproduce.

python
import mlflow

mlflow.set_experiment("churn-model")
with mlflow.start_run():
    mlflow.log_params({"model": "lgbm", "lr": 0.05, "n_estimators": 500})
    model.fit(X_train, y_train)
    auc = roc_auc_score(y_val, model.predict_proba(X_val)[:, 1])
    mlflow.log_metric("val_auc", auc)
    mlflow.sklearn.log_model(model, "model")   # the artifact, versioned
  • MLflow / Weights & Biases — log params, metrics, and artifacts; compare runs in a UI.
  • Pin everything — random seeds, library versions, and the exact data snapshot.
  • Config over hardcoding — drive runs from config files (Hydra), not edited code.

Versioning data, models & code

To reproduce or audit a prediction you need the exact code, data, and model that produced it. Git versions code; you need tools for the rest.

  • Data versioning — DVC or LakeFS track large datasets alongside Git, by hash.
  • Model registry — MLflow Registry stages models (Staging → Production) with lineage back to their run.
  • Immutable artifacts — a deployed model is a fixed version, never an overwritten file.
Note
'Which model is in production right now, trained on what data, by which run?' A senior setup answers that in seconds via the registry.

Packaging & containerizing

Ship the model with its exact environment so it runs identically on a laptop, in CI, and in the cloud. Docker is the standard unit of deployment.

file
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY ./app ./app
COPY model.joblib .
EXPOSE 8000
CMD ["fastapi", "run", "app/main.py", "--port", "8000"]
Note
Use slim or multi-stage builds to keep images small. For GPU inference, start from an official CUDA base image and pin driver-compatible versions.
Core

Serving models

Two serving modes cover most needs. Choose based on whether predictions are needed instantly or can be computed ahead of time.

  • Online (real-time) — a REST/gRPC endpoint returns a prediction per request. Optimize latency.
  • Batch (offline) — score a large dataset on a schedule and store results. Optimize throughput/cost.
  • Tools — FastAPI for custom logic; KServe, BentoML, Ray Serve, or vLLM/TGI (for LLMs) for managed serving and autoscaling.
python
# Minimal online serving with FastAPI (see the FastAPI guide for depth)
import joblib
from fastapi import FastAPI
from pydantic import BaseModel

model = joblib.load("model.joblib")          # loaded once at startup
app = FastAPI()

class Features(BaseModel):
    values: list[float]

@app.post("/predict")
def predict(f: Features):
    proba = float(model.predict_proba([f.values])[0, 1])
    return {"probability": proba}
Try it
Containerize this service and run it locally with docker run -p 8000:8000, then hit /predict. That's a deployable model.

CI/CD for machine learning

ML pipelines extend normal CI/CD with data and model stages: test, train, evaluate against a threshold, and only then deploy — automatically.

config.yaml
# .github/workflows/ml.yml (sketch)
name: ml-pipeline
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt
      - run: pytest                         # code + data validation tests
      - run: python train.py                # train, log to MLflow
      - run: python evaluate.py --min-auc 0.85   # gate: fail if below bar
      - run: python register.py             # promote model in the registry
  • Test the data, not just the code — schema, ranges, nulls (Great Expectations / pandera).
  • Quality gate — block deploys when offline metrics regress below a threshold.
  • Safe rollout — shadow (run new model silently), then canary (small % of traffic) before full.
Senior

Monitoring & drift detection

Unlike normal software, an ML model can fail while every server is green: inputs shift, accuracy decays, but nothing throws an error. Monitoring is what surfaces this silent failure.

  • Operational — latency, throughput, error rate, resource use (the usual SRE metrics).
  • Data drift — input distribution moves away from training data (PSI, KS test).
  • Concept drift — the input→output relationship itself changes; accuracy falls.
  • Model quality — track live metrics once labels arrive; watch prediction distributions in the meantime.
  • Tools — Evidently, WhyLabs, Prometheus + Grafana.
Key idea
Set alerts on drift and quality, not just uptime. The dangerous outage is the one where the service is up but the predictions have quietly gone wrong.
Advanced

Feature stores & training/serving skew

The most insidious production bug: a feature is computed one way in training and another way at serving, so the live model sees inputs it never trained on. A feature store enforces one definition for both.

  • Single source of truth — features defined once, served consistently to training and inference.
  • Online + offline — low-latency lookups for serving, historical values for training.
  • Point-in-time correctness — training features reflect only what was known then (no future leakage).
  • Tools — Feast, Tecton.
Advanced

Retraining, rollback & orchestration

Models decay, so retraining is a scheduled, automated process — with the ability to undo a bad model instantly.

  • Retraining triggers — on a schedule, on drift detection, or on a metric falling below a threshold.
  • Rollback — the registry lets you repoint serving to the previous good version in one step.
  • Orchestration — Airflow / Dagster / Prefect / Kubeflow run multi-step pipelines (ingest → train → eval → deploy) with retries and lineage.
Note
Automate retraining, but keep a human approval gate for promotion to production until your evals are trustworthy enough to trust unattended.

An end-to-end MLOps stack

A recognizably senior project ties the whole lifecycle together:

  • Tracked training with MLflow and a model registry.
  • Versioned data with DVC and validation tests.
  • Containerized serving behind FastAPI, autoscaled.
  • CI/CD with a metric gate and canary deploys.
  • Monitoring for drift and quality, with alerting and one-click rollback.
Key idea
If you can draw this pipeline on a whiteboard and explain each trade-off, you're operating at senior level — this is exactly what ML system design interviews probe.
