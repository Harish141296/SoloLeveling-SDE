Core

REST principles

REST is a style for HTTP APIs: model your domain as resources (nouns) addressed by URLs, and use HTTP methods (verbs) to act on them. Get these conventions right and your API is predictable to every client.

  • Resources & URLs — /users, /users/42, /users/42/orders. Nouns, plural, hierarchical.
  • Methods — GET (read), POST (create), PUT/PATCH (update), DELETE (remove).
  • Idempotency — GET/PUT/DELETE can be safely retried; POST cannot.
  • Statelessness — each request carries everything needed; no server-side session memory of the client.
file
GET    /api/articles          -> list articles            200
POST   /api/articles          -> create one               201 + Location
GET    /api/articles/42       -> fetch one                200 / 404
PATCH  /api/articles/42       -> partial update           200
DELETE /api/articles/42       -> remove                   204
Key idea
Status codes are part of the contract: 2xx success, 4xx the client's fault (400 bad input, 401 unauth, 403 forbidden, 404 missing, 409 conflict), 5xx the server's fault.
Advanced

Designing APIs that scale

Beyond CRUD, real APIs need consistent conventions for large datasets, evolution, errors, and security.

  • Pagination — never return unbounded lists; use limit/offset or cursor paging.
  • Filtering & sorting — ?status=active&sort=-created; document the allowed fields.
  • Versioning — /api/v1/… so you can evolve without breaking existing clients.
  • Consistent errors — one JSON error shape everywhere: a code, a message, optional field details.
  • Auth — stateless tokens (JWT) or OAuth2 in the Authorization header; never in the URL.
json
{
  "data": [ {"id": 42, "title": "REST 101"} ],
  "page": {"limit": 20, "offset": 0, "total": 137},
  "error": null
}
Note
Always pair an API with machine-readable docs. OpenAPI/Swagger lets clients generate SDKs and lets you test interactively — FastAPI does this for free; Django REST Framework via drf-spectacular.
Core

Django: batteries-included web

Django is a mature, full-stack Python framework built for productivity: it ships an ORM, admin panel, auth, migrations, and security out of the box. Its pattern is MVT (Model–View–Template).

terminal
pip install django
django-admin startproject mysite
cd mysite && python manage.py startapp blog
python manage.py runserver
  • Project vs app — a project is the whole site; apps are reusable feature modules.
  • The admin — a production-ready CRUD UI for your models with almost no code.
  • Convention over configuration — sensible defaults so you build features, not plumbing.
Key idea
Reach for Django when you want a complete framework (auth, admin, ORM, templates) and a monolith. Reach for FastAPI when you want a lean, async, API-only service. Both are excellent — different jobs.
Core

Models & the ORM

The Django ORM lets you define your schema as Python classes and query the database without writing SQL. Migrations turn model changes into versioned schema updates.

python
from django.db import models

class Author(models.Model):
    name = models.CharField(max_length=100)

class Article(models.Model):
    title = models.CharField(max_length=200)
    author = models.ForeignKey(Author, on_delete=models.CASCADE,
                               related_name="articles")
    published = models.BooleanField(default=False)
    created = models.DateTimeField(auto_now_add=True)

# Querying
Article.objects.filter(published=True).order_by("-created")[:10]
Article.objects.filter(author__name="Ada")          # join across relation
author.articles.count()                              # reverse relation
terminal
python manage.py makemigrations    # generate migration from model changes
python manage.py migrate           # apply to the database
Note
Watch for the N+1 query trap: use select_related (joins) and prefetch_related to fetch related objects in one go instead of one query per row.

Views, URLs & the request cycle

A view is a function (or class) that takes a request and returns a response. URLs map paths to views. For HTML you render templates; for APIs you return JSON (better via DRF, below).

python
# urls.py
from django.urls import path
from . import views

urlpatterns = [
    path("articles/", views.article_list, name="article-list"),
    path("articles/<int:pk>/", views.article_detail, name="article-detail"),
]

# views.py
from django.shortcuts import render, get_object_or_404
from .models import Article

def article_list(request):
    articles = Article.objects.filter(published=True)
    return render(request, "blog/list.html", {"articles": articles})

def article_detail(request, pk):
    article = get_object_or_404(Article, pk=pk)
    return render(request, "blog/detail.html", {"article": article})
Advanced

Django REST Framework

DRF is the standard way to build APIs in Django. Serializers convert models to/from JSON and validate input; viewsets + routers generate full CRUD endpoints with very little code.

python
from rest_framework import serializers, viewsets, routers
from .models import Article

class ArticleSerializer(serializers.ModelSerializer):
    class Meta:
        model = Article
        fields = ["id", "title", "author", "published", "created"]
        read_only_fields = ["created"]

class ArticleViewSet(viewsets.ModelViewSet):
    queryset = Article.objects.all()
    serializer_class = ArticleSerializer
    # permission_classes, pagination, filtering plug in here

router = routers.DefaultRouter()
router.register("articles", ArticleViewSet)
# -> GET/POST /articles/ and GET/PUT/PATCH/DELETE /articles/{id}/ for free
Key idea
DRF gives you serialization, validation, auth, permissions, pagination, and throttling as composable pieces — the REST design principles from Part 1, implemented for you.
Advanced

Django in production

Taking Django live means hardening settings, serving correctly, and knowing its scaling story.

  • Settings — split dev/prod; load secrets from the environment; DEBUG=False in prod.
  • Security — Django guards CSRF, SQL injection, and XSS by default; keep ALLOWED_HOSTS and HTTPS settings tight.
  • Serving — Gunicorn/Uvicorn workers behind Nginx; static files via WhiteNoise or a CDN.
  • Async & tasks — Django supports async views; offload slow work to Celery (see Data Stores).
  • Caching — Django's cache framework backs onto Redis for sessions, views, and querysets.
Note
Run python manage.py check --deploy before going live — it audits your settings for common production security mistakes.
Senior

Django vs FastAPI vs Flask

A senior engineer picks the right tool for the job and can justify it. All three are production-grade Python web frameworks.

  • Django — full-stack monolith with admin, ORM, auth built in. Best for content-heavy apps, internal tools, fast feature delivery.
  • FastAPI — async, type-driven, auto-documented APIs. Best for high-performance microservices and ML/AI model serving.
  • Flask — minimal and unopinionated. Best for small services where you want to choose every piece yourself.
Key idea
For AI engineering specifically, FastAPI is usually the serving layer of choice (async + Pydantic + OpenAPI). Django shines when the AI feature lives inside a larger product with users, content, and an admin.
Try it
Build the same tiny 'todo' API in both DRF and FastAPI. Feeling the trade-offs firsthand — boilerplate vs control, sync vs async — is the fastest way to develop real judgment.
