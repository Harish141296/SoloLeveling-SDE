Tokenization & embeddings

Models don't read text — they read numbers. Tokenization splits text into sub-word units (tokens); each token maps to an integer id; each id maps to a learned vector (an embedding). That sequence of vectors is what the transformer actually processes.

python
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("gpt2")
ids = tok("Transformers are powerful").input_ids
print(ids)                          # [8291, 16354, 389, 3665]
print(tok.convert_ids_to_tokens(ids))
print(len(tok))                     # vocabulary size
  • BPE / sub-word — balances vocabulary size against handling rare words; 'tokenization' might split into 'token' + 'ization'.
  • Embeddings — dense vectors where similar meanings sit near each other; learned during training.
  • Why it matters — token count drives cost and the context limit. 'Tokens', not words, are the unit you pay for.
Key idea
Rule of thumb: ~1 token ≈ 0.75 English words. A 1,000-word document is roughly 1,300 tokens.

Self-attention: the core mechanism

Attention is the idea that replaced recurrence. For each token, the model asks 'which other tokens should I pay attention to?' and builds a context-aware representation by mixing them. Every token can see every other token directly, in parallel.

Each token produces three vectors: a query (what am I looking for?), a key (what do I offer?), and a value (what I'll contribute). Attention scores = how well each query matches each key; the output is a weighted sum of values.

python
import torch
import torch.nn.functional as F

def scaled_dot_product_attention(Q, K, V, mask=None):
    d_k = Q.size(-1)
    scores = (Q @ K.transpose(-2, -1)) / d_k ** 0.5   # similarity
    if mask is not None:
        scores = scores.masked_fill(mask == 0, float("-inf"))
    weights = F.softmax(scores, dim=-1)               # attention weights
    return weights @ V                                # weighted sum of values
Key idea
This single equation — softmax(QKᵀ/√d)·V — is the heart of every modern LLM. Everything else is scaffolding around it.

Multi-head attention & the transformer block

One attention pattern is limiting, so transformers run several 'heads' in parallel — each can learn a different relationship (syntax, coreference, topic) — then concatenate. A transformer block wraps attention with a feed-forward network, residual connections, and layer norm. Stack dozens of blocks and you have an LLM.

  • Multi-head attention — multiple attention patterns learned in parallel.
  • Feed-forward network — a per-token MLP that adds capacity.
  • Residual connections — let gradients flow through very deep stacks.
  • Layer norm — keeps activations stable across many layers.
Note
'GPT-style' models are just many of these decoder blocks stacked. Model size (e.g. 7B, 70B) counts the parameters across all those blocks.

Positional information

Attention has no built-in sense of order — to it, a sentence is a bag of tokens. Positional encodings inject 'where' each token sits, so the model can tell 'dog bites man' from 'man bites dog.'

  • Sinusoidal / learned — the original approaches, added to embeddings.
  • RoPE (rotary) — the modern standard; rotates query/key vectors by position. Used in most current LLMs.
  • Why you care — positional schemes (and tricks on top of them) determine how far a model's context window can be extended.
Core

Model families & objectives

The same transformer block, arranged differently, yields three families suited to different jobs.

  • Encoder-only (BERT) — sees the whole input at once; great for classification, embeddings, retrieval.
  • Decoder-only (GPT, Llama, Claude-style) — predicts the next token left-to-right; great for generation. This is what 'LLM' usually means today.
  • Encoder–decoder (T5) — reads then writes; natural for translation and summarization.
Key idea
Decoder-only models are trained on one deceptively simple objective — predict the next token — over trillions of tokens. That single task, at scale, produces everything from coding to reasoning.

Pretraining & scaling laws

Capabilities emerge from scale. Scaling laws describe how loss falls predictably as you increase parameters, data, and compute together — and that compute should be split between model size and data (the 'Chinchilla' insight: most early models were under-trained on data).

  • Pretraining — next-token prediction on massive web/text corpora; the expensive base step.
  • Post-training — instruction tuning + preference optimization (RLHF/DPO) turns a raw predictor into a helpful assistant.
  • Emergence — some abilities appear only past a size threshold.
Note
As an engineer you rarely pretrain (it costs millions). You consume base/instruct models and adapt them — the subject of the LLM Engineering guide.

Decoding strategies

Generation is repeated next-token prediction, but how you pick each token from the probability distribution dramatically changes the output.

  • Temperature — flattens (high) or sharpens (low) the distribution. Low = deterministic/factual, high = creative/varied.
  • Top-k / top-p (nucleus) — sample only from the most probable tokens; controls randomness without going off the rails.
  • Greedy / beam — always-best / best-sequence; good for translation, dull for chat.
python
from transformers import AutoModelForCausalLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained("gpt2")
model = AutoModelForCausalLM.from_pretrained("gpt2")

inputs = tok("The future of AI is", return_tensors="pt")
out = model.generate(
    **inputs, max_new_tokens=40,
    do_sample=True, temperature=0.7, top_p=0.9,  # the knobs above
)
print(tok.decode(out[0], skip_special_tokens=True))
Try it
Generate the same prompt at temperature 0.2 and 1.2. Watch one stay safe and repetitive, the other turn wild.

Inference & the KV cache

Generating token N would naively re-process all N-1 previous tokens. The KV cache stores the keys/values already computed so each new token is cheap. Understanding it explains LLM latency and memory.

  • Prefill — process the whole prompt once (compute-bound); this is your 'time to first token.'
  • Decode — generate one token at a time using the cache (memory-bandwidth-bound).
  • Memory cost — the KV cache grows with context length × batch size; it's often the real limit on how many requests a GPU can serve.
Key idea
Serving engines like vLLM (PagedAttention) and TGI exist mostly to manage the KV cache efficiently, enabling high-throughput batched inference.

The HuggingFace ecosystem

HuggingFace is the de-facto hub for open models, datasets, and tooling. The pipeline API gets you running in three lines; AutoModel/AutoTokenizer give you full control.

python
from transformers import pipeline

# Highest-level API: pick a task, get a working model.
summarizer = pipeline("summarization", model="facebook/bart-large-cnn")
print(summarizer(long_text, max_length=80)[0]["summary_text"])

embedder = pipeline("feature-extraction", model="sentence-transformers/all-MiniLM-L6-v2")
# embeddings power the RAG systems in the LLM Engineering guide
Note
For production text embeddings, sentence-transformers is the standard. You'll use it constantly for RAG and semantic search.

Context, cost & failure modes

To use LLMs responsibly you must know where they break. These limits drive almost every architectural decision in the LLM Engineering guide.

  • Hallucination — fluent, confident, wrong. Mitigated with retrieval (RAG) and grounding, not eliminated.
  • Context window — finite token budget for prompt + output; long inputs cost more and can dilute attention.
  • Knowledge cutoff — the base model only knows its training data; current facts need tools or retrieval.
  • Cost & latency — scale with tokens; bigger models cost more and respond slower.
  • Prompt sensitivity — small wording changes shift outputs; this is why evals matter.
