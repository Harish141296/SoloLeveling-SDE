Core

SQL fundamentals

SQL is the lingua franca of data, and fluency is non-negotiable for backend and AI engineers alike. The core is querying: selecting, filtering, joining, and aggregating relational data.

file
-- Filter and sort
SELECT id, title, created
FROM articles
WHERE published = true
ORDER BY created DESC
LIMIT 10;

-- Join related tables
SELECT a.title, u.name AS author
FROM articles a
JOIN users u ON u.id = a.author_id
WHERE u.active = true;

-- Aggregate with GROUP BY
SELECT author_id, COUNT(*) AS n, MAX(created) AS latest
FROM articles
GROUP BY author_id
HAVING COUNT(*) > 5;
  • JOINs — INNER (matches only), LEFT (keep all left rows); the heart of relational queries.
  • WHERE vs HAVING — WHERE filters rows, HAVING filters groups after aggregation.
  • NULL is special — use IS NULL, not = NULL; NULL breaks naive comparisons.
Key idea
Most 'big data' problems are solved with a well-written SQL query long before you need anything fancier. Invest here — it pays off in every role.
Advanced

Advanced SQL & performance

Window functions, CTEs, and indexes are what separate someone who 'knows SQL' from someone who can make it fast and expressive at scale.

file
-- CTE + window function: rank articles per author by recency
WITH ranked AS (
  SELECT title, author_id,
         ROW_NUMBER() OVER (PARTITION BY author_id ORDER BY created DESC) AS rn
  FROM articles
)
SELECT * FROM ranked WHERE rn <= 3;       -- top 3 per author

-- Indexes make lookups fast; check the plan to confirm they're used
CREATE INDEX idx_articles_author ON articles(author_id);
EXPLAIN ANALYZE SELECT * FROM articles WHERE author_id = 42;
  • Window functions — ranking, running totals, per-group analytics without collapsing rows.
  • CTEs (WITH) — name subqueries to make complex logic readable.
  • Indexes — turn full-table scans into instant lookups; index columns you filter/join on.
  • EXPLAIN — read the query plan to find slow scans and missing indexes.
Note
Indexes speed reads but slow writes and use space. Index deliberately — measure with EXPLAIN ANALYZE rather than guessing.

PostgreSQL specifics

PostgreSQL is the default choice for serious applications: open-source, rock-solid, standards-compliant, and packed with features beyond plain SQL.

  • Rich types — JSONB (indexed JSON), arrays, ranges, UUID, full-text search.
  • ACID transactions — wrap multiple statements so they all succeed or all roll back.
  • Constraints — primary/foreign keys, UNIQUE, CHECK enforce integrity at the database.
  • Extensions — pgvector for embeddings (RAG!), PostGIS for geo, and more.
file
BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- both happen, or neither (ROLLBACK on error)

-- JSONB: store and query semi-structured data
SELECT data->>'email' FROM users WHERE data->>'plan' = 'pro';
Key idea
For AI engineers: PostgreSQL + the pgvector extension is a popular, simple vector store for RAG — your relational data and embeddings live in one database.
Core

Schema design & migrations

A good schema prevents whole classes of bugs. Model relationships explicitly, normalize to avoid duplication, and evolve the schema with versioned migrations — never by hand in production.

  • Normalize — each fact lives in one place; relate tables with foreign keys.
  • Keys & constraints — let the database enforce correctness, not just your app code.
  • Migrations — every schema change is a reviewed, reversible, version-controlled step (Django migrations, Alembic).
Note
Denormalize only when measured performance demands it — and document why. Premature denormalization is a common source of data-integrity bugs.

Redis: the in-memory workhorse

Redis is a blazingly fast in-memory data store. Because it lives in RAM, reads/writes take microseconds — perfect for caching, sessions, counters, queues, and real-time features.

python
import redis
r = redis.Redis(host="localhost", port=6379, decode_responses=True)

r.set("user:42:name", "Ada", ex=3600)   # value with 1-hour expiry (TTL)
r.get("user:42:name")

r.incr("page:home:views")                # atomic counter
r.lpush("queue:emails", "job-1")         # list as a simple queue
r.sadd("online", "user:42")              # set membership
r.expire("session:abc", 1800)            # auto-expire keys
  • Data structures — strings, hashes, lists, sets, sorted sets, streams — not just key/value.
  • TTL — keys can auto-expire, which makes caching trivial.
  • Atomic ops — INCR and friends are safe under concurrency.
Advanced

Caching patterns & beyond

The most common Redis use is caching expensive results to cut latency and database load. Get the pattern — and invalidation — right.

python
import json

def get_user(user_id):
    key = f"user:{user_id}"
    cached = r.get(key)
    if cached:
        return json.loads(cached)        # cache HIT
    user = db.query_user(user_id)        # cache MISS -> hit the DB
    r.set(key, json.dumps(user), ex=300) # store for 5 minutes
    return user
  • Cache-aside — check cache, fall back to DB, then populate the cache (above).
  • Invalidation — the hard part; expire with TTL and/or delete keys on write.
  • Rate limiting — INCR + EXPIRE per user/IP to throttle requests.
  • Pub/Sub & streams — lightweight real-time messaging between services.
  • As a broker — Redis often backs task queues like Celery (next).
Key idea
“There are only two hard things in computer science: cache invalidation and naming things.” Default to short TTLs and explicit deletes on update.

Celery: background task queues

Web requests must be fast, but some work is slow — sending email, processing uploads, calling an LLM, generating reports. Celery moves that work to background workers so the request returns immediately.

python
# tasks.py
from celery import Celery

app = Celery("myapp", broker="redis://localhost:6379/0",
                      backend="redis://localhost:6379/1")

@app.task
def send_welcome_email(user_id):
    user = db.query_user(user_id)
    mailer.send(user.email, "Welcome!")
    return "sent"

# In your web request — enqueue and return instantly
send_welcome_email.delay(user_id=42)     # non-blocking; a worker runs it
terminal
# A worker process consumes and runs queued tasks
celery -A tasks worker --loglevel=info
  • Broker — the queue tasks wait in (Redis or RabbitMQ).
  • Worker — a separate process that pulls tasks and executes them.
  • Backend — where results are stored (optional).
Note
This is how CPU-bound or slow work scales in Python: hand it to workers you can run many of, independent of your web servers.
Advanced

Celery in production

Background jobs fail, retry, and need scheduling. Production Celery is about making tasks reliable and observable.

  • Retries — autoretry_for with exponential backoff for flaky external calls.
  • Idempotency — design tasks so running twice is safe (they may be retried).
  • Scheduling — Celery Beat runs periodic tasks (nightly reports, cleanup) like cron.
  • Routing & concurrency — separate queues for fast vs slow work; scale workers independently.
  • Monitoring — Flower (or your metrics stack) to watch queue depth, failures, and latency.
python
@app.task(autoretry_for=(ConnectionError,), retry_backoff=True, max_retries=5)
def call_external_api(payload):
    return httpx.post("https://api.example.com", json=payload).json()
Try it
Wire up Redis + Celery locally and offload a slow task from a FastAPI or Django endpoint. Watch the request return instantly while the worker logs the job — that's the pattern behind responsive apps.
