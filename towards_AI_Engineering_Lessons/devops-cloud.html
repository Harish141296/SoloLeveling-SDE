Foundational

Linux & the command line

Servers run Linux, containers run Linux, CI runs Linux. Being fluent at the shell is a baseline skill — you'll use it every day to inspect, debug, and operate systems.

terminal
# Navigate & inspect
ls -lah                 # list with sizes, hidden files
cd /var/log && pwd
cat app.log | grep ERROR | tail -20     # pipes: chain small tools

# Files, permissions, processes
chmod +x deploy.sh                       # make executable
chown user:group file
ps aux | grep python                     # find a process
kill -9 <pid>                            # stop it
df -h ; free -m ; top                    # disk, memory, live processes
  • Pipes & redirection — | chains commands, >/>> write to files; the Unix philosophy of small composable tools.
  • Permissions — read/write/execute for user/group/other; the source of many 'it works locally' bugs.
  • Everything is a file — processes, devices, and config all live in the filesystem.
Key idea
Learn grep, find, sed, awk, ssh, and an editor (vim/nano). They're how you'll debug a production box at 2am with nothing but a terminal.
Foundational

Git: version control

Git tracks every change and lets teams collaborate without overwriting each other. Beyond add/commit/push, seniority means comfort with branching, history, and conflict resolution.

terminal
git checkout -b feature/login       # branch off main
# ...make changes...
git add -p                          # stage hunks interactively
git commit -m "feat: add login flow"
git push -u origin feature/login    # open a Pull Request from here

# Keeping up to date & cleaning history
git pull --rebase origin main       # replay your work on top of latest main
git rebase -i HEAD~3                # squash/reword recent commits
git log --oneline --graph           # visualize history
  • Branch per change — short-lived feature branches merged via reviewed Pull Requests.
  • merge vs rebase — merge preserves history; rebase keeps it linear. Don't rebase shared branches.
  • Conflicts — normal; resolve the marked sections, test, then continue.
  • Good commits — small, focused, with clear messages (Conventional Commits help).
Note
A clean Git history is a gift to your future self and reviewers. Commit often locally; tidy up with interactive rebase before opening a PR.
Core

Docker: containers

Docker packages your app with its exact environment into an image that runs identically anywhere — your laptop, CI, and production. It ends 'works on my machine' for good.

file
# Multi-stage Dockerfile: small, reproducible image
FROM python:3.12-slim AS base
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["fastapi", "run", "app/main.py", "--port", "8000"]
terminal
docker build -t myapp:1.0 .          # build an image
docker run -p 8000:8000 myapp:1.0    # run a container from it
docker ps                            # list running containers
docker compose up -d                 # run a multi-service stack (app+db+redis)
  • Image vs container — image is the blueprint; a container is a running instance.
  • Layers — each Dockerfile line is a cached layer; order them so dependencies cache well.
  • Volumes & networks — persist data and let containers talk to each other.
  • Compose — define app + Postgres + Redis together in one YAML file for local dev.
Advanced

Kubernetes: orchestration

When you run many containers across many machines, Kubernetes (K8s) schedules them, restarts failures, scales on demand, and rolls out updates safely. It's the standard for production container orchestration.

config.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: myapp }
spec:
  replicas: 3                     # run 3 copies for availability
  selector: { matchLabels: { app: myapp } }
  template:
    metadata: { labels: { app: myapp } }
    spec:
      containers:
        - name: myapp
          image: myapp:1.0
          ports: [ { containerPort: 8000 } ]
          resources:
            requests: { cpu: "250m", memory: "256Mi" }
            limits:   { cpu: "500m", memory: "512Mi" }
  • Pod — the smallest unit; one or more containers that run together.
  • Deployment — declares the desired state (e.g. 'always 3 replicas'); K8s makes it so.
  • Service — a stable network address load-balancing across pods.
  • ConfigMaps / Secrets — inject config and credentials without baking them into images.
  • Ingress — routes external HTTP traffic to services.
Key idea
You declare the desired state; Kubernetes continuously reconciles reality to match it. That declarative, self-healing model is the whole point.

CI/CD pipelines

CI (continuous integration) runs your tests automatically on every push; CD (continuous delivery/deployment) automatically ships code that passes. Together they make releases boring — which is exactly what you want.

config.yaml
# .github/workflows/ci.yml — GitHub Actions
name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -e ".[dev]"
      - run: ruff check .          # lint
      - run: mypy app/             # types
      - run: pytest --cov=app      # tests + coverage  (gate the merge)
  deploy:
    needs: test                    # only if tests pass
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - run: echo "build image, push, roll out..."
  • Fast feedback — every PR is automatically linted, type-checked, and tested.
  • Quality gate — merges are blocked unless the pipeline is green.
  • Safe rollout — build once, deploy via blue-green or canary; automate rollback.
Note
Pair CI/CD with the tests from the Python guide: tests are only as valuable as their automatic execution on every change.
Advanced

AWS: the core services

AWS is the largest cloud provider. You don't need all 200+ services — a handful covers most application needs, and the concepts transfer to any cloud.

  • Compute — EC2 (virtual machines), Lambda (serverless functions), ECS/EKS (containers/K8s).
  • Storage — S3 (object storage for files/backups/datasets), EBS (disks).
  • Databases — RDS (managed PostgreSQL/MySQL), DynamoDB (NoSQL), ElastiCache (managed Redis).
  • Networking & security — VPC (private networks), IAM (who can do what — least privilege!).
  • AI — SageMaker (ML platform), Bedrock (managed foundation models).
Key idea
IAM is where security lives and breaks. Grant least privilege, never hard-code credentials (use roles), and keep secrets in Secrets Manager — not in code or images.
Advanced

Azure: the equivalents

Microsoft Azure is the other dominant cloud, common in enterprises. The building blocks mirror AWS — learn one deeply and you can navigate the other.

  • Compute — Virtual Machines, Azure Functions (serverless), AKS (managed Kubernetes).
  • Storage — Blob Storage (≈ S3), Managed Disks.
  • Databases — Azure Database for PostgreSQL, Cosmos DB (NoSQL), Azure Cache for Redis.
  • Identity — Microsoft Entra ID (formerly Azure AD) for auth and access control.
  • AI — Azure Machine Learning and Azure OpenAI Service.
Note
Concepts are portable: compute, object storage, managed databases, identity/IAM, and serverless exist on every cloud. Master the model once; map the names per provider.
Senior

Cloud fundamentals & IaC

Beyond individual services, senior cloud work is about reliability, cost, and reproducibility across whatever provider you're on.

  • Regions & availability zones — deploy across zones for resilience; pick regions near users.
  • Scaling — autoscaling groups / horizontal pod autoscalers respond to load.
  • Cost engineering — right-size instances, use spot/savings plans, watch egress and idle resources.
  • Infrastructure as Code — define infrastructure in Terraform so it's versioned, reviewed, and reproducible — never click-ops in production.
file
# Terraform: declarative, version-controlled infrastructure
resource "aws_s3_bucket" "uploads" {
  bucket = "myapp-uploads-prod"
}

resource "aws_db_instance" "db" {
  engine         = "postgres"
  instance_class = "db.t3.micro"
  allocated_storage = 20
}
Try it
Containerize an app (Docker), push it to a registry, and deploy it to a managed container service on one cloud. Doing the full path once — code → image → cloud → live URL — demystifies the entire stack.
