Core

Prompt engineering that holds up

Prompting is the cheapest lever and the first thing to exhaust before reaching for RAG or fine-tuning. Production prompts are engineered artifacts — versioned, tested, and templated — not chat messages.

  • System prompt — set role, constraints, tone, and output format up front.
  • Few-shot — show 2–5 examples of exactly the input→output you want.
  • Chain-of-thought — ask the model to reason step by step for complex tasks.
  • Be specific — spell out format, length, and what to do on uncertainty.
python
import anthropic
client = anthropic.Anthropic()   # reads ANTHROPIC_API_KEY

resp = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=512,
    system=("You are a precise data extraction assistant. "
            "Return ONLY valid JSON. If a field is missing, use null."),
    messages=[{"role": "user", "content": f"Extract name, email, company:\n{text}"}],
)
print(resp.content[0].text)
Key idea
Treat prompts like code: store them in version control, parameterize with templates, and cover them with evals so a 'small wording tweak' can't silently break production.

Structured output & function calling

Apps need machine-readable output, not prose. Two reliable techniques: instruct-and-validate JSON, and tool/function calling where the model returns a structured call you execute.

Retrieval-Augmented Generation

LLMs hallucinate and don't know your private or recent data. RAG fixes both: retrieve relevant documents at query time and put them in the prompt, so the model answers from real, current sources it can cite.

  • Index (offline) — chunk documents, embed each chunk, store vectors in a vector DB.
  • Retrieve (online) — embed the query, find the nearest chunks.
  • Generate — stuff the retrieved chunks into the prompt and ask the model to answer from them.
Key idea
RAG is the default architecture for 'chat with my docs / knowledge base.' It's grounding, not memorization — and it lets you update knowledge by re-indexing, no retraining.

Building a minimal RAG pipeline

A complete, runnable RAG loop with open tools: sentence-transformers for embeddings, Chroma for storage.

python
import chromadb
from sentence_transformers import SentenceTransformer

embedder = SentenceTransformer("all-MiniLM-L6-v2")
db = chromadb.Client().create_collection("docs")

# --- INDEX (offline) ---
def chunk(text, size=500, overlap=50):
    return [text[i:i+size] for i in range(0, len(text), size - overlap)]

chunks = chunk(document_text)
db.add(ids=[str(i) for i in range(len(chunks))],
       documents=chunks,
       embeddings=embedder.encode(chunks).tolist())

# --- RETRIEVE + GENERATE (online) ---
def answer(question, k=4):
    q_emb = embedder.encode([question]).tolist()
    hits = db.query(query_embeddings=q_emb, n_results=k)["documents"][0]
    context = "\n---\n".join(hits)
    prompt = (f"Answer using ONLY the context. If it's not there, say so.\n\n"
              f"Context:\n{context}\n\nQuestion: {question}")
    resp = client.messages.create(model="claude-sonnet-4-6", max_tokens=400,
                                  messages=[{"role": "user", "content": prompt}])
    return resp.content[0].text
Try it
Index a few of your own documents and ask questions. Then ask something not in them — a good prompt makes the model say 'not found' instead of inventing.
Advanced

Better retrieval: chunking, hybrid & reranking

Naive RAG retrieves irrelevant chunks and the answer suffers. Retrieval quality is where most RAG systems live or die — invest here before touching the LLM.

  • Smart chunking — split on semantic boundaries (headings, paragraphs), not blind character counts; tune size/overlap.
  • Hybrid search — combine dense (embedding) with sparse (BM25 keyword) for the best of both.
  • Reranking — retrieve 20 candidates, then a cross-encoder reranker scores and keeps the top 4.
  • Metadata filtering — restrict by source, date, or permissions before semantic search.
Note
Always evaluate retrieval separately from generation. Measure recall@k on a labeled set: if the right chunk isn't retrieved, no LLM can answer correctly.

Agents & tool use

An agent is an LLM in a loop that can call tools (functions, APIs, search, code execution), observe the results, and decide the next step. This is how LLMs act on the world instead of just talking about it.

python
tools = [{
    "name": "get_weather",
    "description": "Get current weather for a city",
    "input_schema": {"type": "object",
                     "properties": {"city": {"type": "string"}},
                     "required": ["city"]},
}]

resp = client.messages.create(
    model="claude-sonnet-4-6", max_tokens=400, tools=tools,
    messages=[{"role": "user", "content": "What's the weather in Tokyo?"}],
)

# The model returns a tool_use block; you run the tool and feed the result back.
for block in resp.content:
    if block.type == "tool_use":
        result = run_tool(block.name, block.input)      # your code executes it
        # append tool_result to messages and call again -> the agent loop
  • The loop — think → call tool → observe → repeat until done.
  • MCP — the Model Context Protocol standardizes how agents connect to tools and data sources.
  • Guard the loop — cap iterations, validate tool inputs, and sandbox anything that runs code.
Advanced

Memory, planning & multi-agent

Beyond a single loop, real agentic systems need state and structure — but add complexity only when a simpler design fails.

  • Memory — short-term (conversation), long-term (vector store of past interactions), scratchpad for working state.
  • Planning — decompose a goal into sub-tasks; reflect on failures and retry.
  • Multi-agent — specialized agents (planner, researcher, critic) that hand off; powerful but harder to debug.
Key idea
Senior judgment: most 'agent' problems are solved better by a well-structured workflow with one or two tool calls than by an open-ended autonomous agent. Reach for autonomy last.
Advanced

Fine-tuning: when and how

Fine-tuning adjusts a model's weights on your data. It's powerful but often the wrong first move — prompting and RAG are cheaper and faster to iterate.

  • Use prompting/RAG for — adding knowledge, changing facts, most tasks.
  • Use fine-tuning for — a consistent style/format, a narrow specialized task, or cutting prompt length/latency at scale.
  • LoRA / QLoRA — train tiny adapter matrices instead of all weights; fine-tune a large model on a single GPU.
python
from peft import LoraConfig, get_peft_model
from transformers import AutoModelForCausalLM

base = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.1-8B")
lora = LoraConfig(r=16, lora_alpha=32, target_modules=["q_proj", "v_proj"],
                  lora_dropout=0.05, task_type="CAUSAL_LM")
model = get_peft_model(base, lora)
model.print_trainable_parameters()   # often <1% of params are trained
# then train with trl's SFTTrainer on your instruction dataset
Note
Fine-tuning teaches behavior, not facts. To add knowledge, prefer RAG — fine-tuning facts in is expensive and they go stale.
Senior

Evaluation: the senior differentiator

You cannot improve what you don't measure, and LLM output is hard to measure. Teams that win build evals early; teams that ship on vibes regress silently.

  • Golden dataset — curated input→expected pairs that represent real usage; your regression suite.
  • LLM-as-judge — use a strong model with a rubric to score outputs at scale; calibrate it against human labels.
  • Component evals — measure retrieval (recall@k), generation (faithfulness), and the end-to-end task separately.
  • Regression testing — run evals in CI on every prompt/model change.
python
def judge(question, answer, reference):
    rubric = (f"Question: {question}\nReference: {reference}\nAnswer: {answer}\n"
              "Score 1-5 for correctness and groundedness. Return JSON "
              '{"score": int, "reason": str}.')
    r = client.messages.create(model="claude-sonnet-4-6", max_tokens=200,
                               messages=[{"role": "user", "content": rubric}])
    return r.content[0].text
Key idea
'It looks good' is not evaluation. A golden set + automated scoring in CI is what lets you change models or prompts with confidence.
Senior

Guardrails, reliability & cost

Production LLM systems need defenses and budgets. This is the operational layer that separates a demo from a product users trust.

  • Input guards — detect prompt injection, off-topic, or unsafe requests before they reach the model.
  • Output guards — validate structure, filter unsafe content, check groundedness/citations.
  • Reliability — timeouts, retries with backoff, fallbacks to a smaller model, graceful degradation.
  • Cost & latency — cache repeated calls, route easy queries to small models, trim context, stream responses.
  • Serving — for self-hosted models, vLLM/TGI for batched, KV-cache-efficient inference; quantize to fit GPUs.
Try it
Add a cache keyed on the prompt to your RAG app, then measure cost and latency on repeated questions. Caching is often the highest-ROI optimization.
